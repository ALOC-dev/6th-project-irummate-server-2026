# 채팅 전송 성능 측정과 최적화 계획

## 구현 전 측정

2026-11-19에 로컬 PostgreSQL 17.10과 WebSocket 통합 테스트 환경에서 측정했다. 각 시나리오는 워밍업 후 이벤트 100건을 초당 약 10건으로 실행했다. p95는 측정값의 95%가 그 값 이하였음을 뜻한다.

| 측정 구간 | 이벤트당 SQL | 소요 시간 p95 | DB 연결 대기 p95 |
|---|---:|---:|---:|
| 1:1 실제 전송부터 상대의 메시지·알림 수신까지 | 조회 13회, 저장 1회 | 38.52ms | 0.019ms |
| 1:1 권한 검사, 연결별 조회 | 조회 2회 | 5.30ms | 0.016ms |
| 1:1 권한 검사, 이벤트당 일괄 조회 | 조회 1회 | 4.07ms | 0.018ms |
| 단체방 10명·20개 세션 권한 검사, 연결별 조회 | 조회 20회 | 32.88ms | 0.005ms |
| 단체방 10명·20개 세션 권한 검사, 이벤트당 일괄 조회 | 조회 1회 | 3.50ms | 0.028ms |

첫 행은 현재 1:1 전송 전체를 잰 값이다. 나머지 행은 수신자 자격과 로그인 세션 상태를 확인하는 DB 구간만 잰 값이다.

## 실시간 전달 구현 및 재측정

1. 현재 방 멤버와 유효한 수신 세션을 이벤트당 한 번에 조회한다. 이미 열린 연결에서 강퇴 후 수신이 차단되는지, 수신자 조회와 강퇴가 겹치는 경우까지 통합 테스트로 확인한다.
2. 구현 후 k6에서 실제 STOMP 연결을 열고, 1:1 방과 10명·20개 연결 단체방을 각각 초당 약 10건으로 측정한다. 발신부터 수신까지의 p95와 누락률을 기록하고, 서버의 메시지당 SQL 실행 수와 Hikari 연결 대기 p95를 같은 구간에서 수집한다.
3. 재측정 결과를 보고 기존 1:1 전송 경로의 쿼리 개선 우선순위를 정한다. 개선 후보는 메시지 저장과 알림 생성에서 발신자를 각각 조회하는 부분과, 이때 Hibernate가 추가로 조회하는 `user_details`, `user_preferences`다.
